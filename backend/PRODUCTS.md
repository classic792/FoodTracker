# Product API (FET-6)

Products are catalog entries referenced by batches. All endpoints below require the staff session cookie established by `POST /api/auth/login`; browser clients must use `credentials: "include"`. See [AUTH.md](./AUTH.md) for authentication, cookie lifetime, and origin configuration. Product responses have `Cache-Control: no-store`.

No product seeds, fixtures, schema changes, or migrations were added. Batch, storage-location, and stock-movement endpoints are not part of this feature.

## Endpoints

| Method and path | Accepted input | Success |
| --- | --- | --- |
| `POST /api/products` | Required `productCode`, `name`, `stockUnit`; optional `description` | `201`, product object |
| `GET /api/products` | Query `q`, `page`, `pageSize` | `200`, `{ items, page, pageSize, total, totalPages }` |
| `GET /api/products/:id` | UUID path parameter | `200`, product object |
| `PATCH /api/products/:id` | UUID; body containing `name` and/or `description` | `200`, updated product object |
| `DELETE /api/products/:id` | UUID path parameter | `204`, empty body |

Product objects contain exactly `id`, `productCode`, `name`, `stockUnit`, `description`, `createdAt`, and `updatedAt`. Dates are ISO-8601 strings and description may be `null`. Single products are returned directly without a wrapper or embedded batches. IDs are generated by the service with `crypto.randomUUID()`.

## Validation and fixed fields

- Required strings are trimmed and cannot be blank. Maximum lengths: product code 50 characters, name 150, stock unit 30. Null is not valid for these fields.
- Product codes retain case: `RICE-001` and `rice-001` are distinct codes. Surrounding spaces are removed before storage. Uniqueness is enforced by the database, including concurrent creates.
- Stock unit is free text, not an enum. Both `productCode` and `stockUnit` are immutable after creation. PATCH rejects either field whenever supplied, even if unchanged, with `400 VALIDATION_ERROR` and respectively `"productCode cannot be changed after creation."` or `"stockUnit cannot be changed after creation."`.
- Description accepts a string or `null`. Strings are trimmed; blank strings become `null`. Omission on creation stores `null`; omission on PATCH preserves the current description. Explicit `null` clears it.
- PATCH accepts only name and description, requires at least one field, preserves unspecified fields, and explicitly updates `updatedAt`.
- Unknown body/query fields, invalid UUIDs, empty PATCH bodies, invalid types, and invalid pagination return `400 VALIDATION_ERROR`. Request bodies must be JSON objects; the existing JSON body-size limit applies.

## List and search

`GET /api/products?q=rice&page=1&pageSize=20` returns products whose name or code contains the search text, case-insensitively. `q` is trimmed; blank/omitted means no filter. Search uses Prisma `contains` with PostgreSQL's case-insensitive matching (SQL pattern characters `%` and `_` retain their pattern behavior).

Pagination defaults to `page=1` and `pageSize=20`. Both must be positive integers; page size cannot exceed 100 and page cannot exceed 2,147,483,647. The computed offset `(page - 1) * pageSize` must also be at most 2,147,483,647. Invalid values are rejected, not clamped. Repeated query values are rejected as invalid types.

Results are ordered by name ascending, then ID ascending. `total` counts all matching products, and `totalPages` is `ceil(total / pageSize)` (zero when there are no matches). A page beyond the results returns `items: []`, preserving the requested valid page and actual totals. Ordering is deterministic for unchanged data; offset pagination does not freeze the catalog between requests, and concurrent writes can change pages/totals.

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0,
  "totalPages": 0
}
```

## Errors and deletion safety

Errors use the existing envelope:

```json
{
  "error": {
    "code": "DUPLICATE_PRODUCT_CODE",
    "message": "A product with this code already exists."
  }
}
```

| HTTP status | Code | Message / cause |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | Field-specific validation message; immutable messages are specified above |
| `400` | `INVALID_JSON` | `Request body must be valid JSON.` |
| `401` | `UNAUTHORIZED` | `Authentication required.` |
| `403` | `ORIGIN_FORBIDDEN` | `Request origin is not allowed.` |
| `404` | `PRODUCT_NOT_FOUND` | `Product not found.` |
| `409` | `DUPLICATE_PRODUCT_CODE` | `A product with this code already exists.` |
| `409` | `PRODUCT_IN_USE` | `This product has batches on record and cannot be deleted.` |
| `413` | `PAYLOAD_TOO_LARGE` | `Request body is too large.` |
| `500` | `INTERNAL_ERROR` | `An unexpected error occurred.` |

Missing, invalid, expired, or inactive-account sessions are rejected before product controllers/services run. Existing global origin and JSON parsing middleware still execute before the product router. Unsupported URLs use the shared `404 NOT_FOUND` response.

Deletion is a hard delete. A product referenced by any batch, including a batch with zero quantity, cannot be deleted: PostgreSQL's existing `onDelete: Restrict` foreign key is the safeguard. The service translates Prisma `P2003` into `409 PRODUCT_IN_USE`, without counting batches or relying on a race-prone pre-check. Missing products return `404 PRODUCT_NOT_FOUND` for retrieval, editing, and deletion. Unexpected database errors are not exposed.

## Manual request examples (not executed)

First log in using a development staff account from [SEED_USERS.md](./SEED_USERS.md). Reuse its cookie for every request below.

Create: `POST /api/products`

```json
{
  "productCode": "RICE-001",
  "name": "Rice",
  "stockUnit": "bag",
  "description": "5 kg bag"
}
```

Expected: `201` with the product below (UUID and timestamps are illustrative):

```json
{
  "id": "27e86422-daf3-453a-94be-d6c26cb3cb84",
  "productCode": "RICE-001",
  "name": "Rice",
  "stockUnit": "bag",
  "description": "5 kg bag",
  "createdAt": "2026-09-25T10:00:00.000Z",
  "updatedAt": "2026-09-25T10:00:00.000Z"
}
```

Repeating the create returns `409 DUPLICATE_PRODUCT_CODE`. Using the generated ID, `GET /api/products/:id` returns the same product with `200`.

Edit: `PATCH /api/products/:id`

```json
{
  "name": "Long-grain rice",
  "description": null
}
```

Expected: `200`, preserving ID, code, unit, and creation time while updating name, clearing description, and advancing `updatedAt`. Sending `{ "stockUnit": "bag" }` instead returns `400 VALIDATION_ERROR`, even though that unit matches the stored value. The same applies to `{ "productCode": "RICE-001" }`.

Delete: `DELETE /api/products/:id`, no body. Expected: `204` and no response body if no batches reference the product; otherwise `409 PRODUCT_IN_USE`. A repeated successful deletion returns `404 PRODUCT_NOT_FOUND`.

## Manual verification checklist

- Valid active session can use all five endpoints; missing, invalid, expired, and inactive-account sessions return `401` on otherwise valid requests.
- Missing, null, blank, overlength, wrong-type, and unknown fields produce `400`; whitespace trimming preserves code casing.
- Duplicate code creation, including concurrent attempts, produces `409`; a casing variant remains a distinct code.
- Name-only, description-only, null-description, and blank-description PATCH requests preserve other fields and update the timestamp. Empty bodies and fixed fields are rejected.
- Search matches name or code regardless of casing; blank search lists all products. Verify default pagination, maximum size 100, invalid/repeated parameters, excessive offsets, equal-name ordering, and empty/out-of-range results.
- Invalid UUIDs return `400`; a valid UUID with no product returns `404` for GET, PATCH, and DELETE.
- Unreferenced product deletion succeeds; a product with any existing batch cannot be deleted and retains its data after `409`.
- Origin rejection, malformed JSON, and oversized bodies retain the shared errors above.

Implementation verification is limited to JavaScript syntax checks and Prisma schema validation. No endpoint tests, test files, product seeds, fixtures, or database writes were performed as verification.
